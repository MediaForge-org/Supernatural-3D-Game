# Night Build 01 — known issues, limitations and unverified items

## Regressions
None known as of the final test run (see `QA_RESULTS.md`). The two movement failures below pre-date this work.

## Unresolved (pre-existing)
* **`SpnGame.Movement.Obstacles` and `SpnGame.Movement.StairsAndRamps` fail** (a 30 cm ledge / a 30 cm staircase are walked up). Root cause not found; see `OPUS_ESCALATION.md`. Not widened, not weakened.
* **`late_jump_ledge_45_jog`, `late_jump_ledge_40_run` and the intermittent `MovementDemo.ledge_80_blocks_even_with_a_jump` were NOT investigated** (the time went into the 30 cm question and the integrated features). They belong to the `SpnQA.*` movement suites, which were not re-run in this build unless `QA_RESULTS.md` says so.

## Limitations of what was built
* **Test data only.** The map is a 400 m placeholder derived from the test level; no terrain art, no real POI data, no WorldForge data. All screens say so.
* **Navigation is a straight line.** No pathfinding, roads or obstacle awareness. The UI says "direct line".
* **(Resolved in the completion pass)** The player position IS saved now (`player.pose`). Remaining limits: velocity and fall state are not saved; a pose in a level that no longer exists, or without ground below it, is refused with a notice and the player starts at the level start.
* **Actors are recreated, not saved.** Core `ObjectPersistence` is deliberately not integrated (see `COMPLETION_REPORT.md` section 5); containers and pickups exist because the level / scenario spawner creates them and they match the saved facts and inventory. Only the scenario objects of `Lvl_SpnMovementTestV3Interiors` exist.
* **No partial pickup** (the Core transaction is all-or-nothing).
* **Audio:** master volume (`FApp::SetVolumeMultiplier`) plus music and effects volume, which set the volume of the engine sound classes `/Engine/EngineSounds/Music` and `/SFX` in memory. **No sound in this project uses those classes yet, so the two sliders currently change nothing audible**; the settings page says so. Persistence of all three was tested by reloading the ini, not across a real process restart.
* **"UI navigation settings"** (work package G) are not implemented: no concrete setting with a real effect was identified.
* **Controller:** the gamepad paths (menu, map, HUD hints) are implemented, but **no physical DualSense was used; nothing was validated with hardware.** Triangle for the map is a placeholder; Square/Circle/Cross are used only inside modal screens; no gameplay mapping was changed.
* **Pause pauses the whole world** (single player). Co-op needs a different rule.
* **Inventory UI 2.0:** list/grid, sort, category filter, grid navigation and weight/volume/condition rows exist. **Not done:** a redesigned equipment panel, verification of responsive layouts other than 16:9 (the screen scales to fit a 1840x1000 design, which letterboxes at other aspect ratios), real icons (coloured letter swatches only). The grid has 6 fixed columns.
* **Interaction (J):** doors, pickups and containers work through the existing interaction component (prompt, range, line of sight by sweep). There is no new interaction-availability rule beyond "taken" and "capacity", and no context-sensitive attack integration.
* **Windows-only validation.** Clang/Fedora builds of the Unreal module were not attempted; the portable Core was not changed.
* **Video:** scripted input (OS-level keyboard events and relative mouse movement into the game window), not manual play. The completion run (`Saved/NightBuild01/completion-video/`) uses NO teleport: the script reads the player pose from a QA feed and steers with the mouse like eyes would. One interaction (the cupboard) needed a second try; it is logged in `steps.txt`. Stairs/ramps are not part of the scenario (covered by the movement suites, two of which fail, see above). The earlier video (`final-video/`) used the F5 teleport hook between objects.
* **Simulated vs hardware input:** keys are injected through Slate / OS input; a physical DualSense and keyboard layouts other than the development machine were never used.
* **Headless vs rendered:** `SpnQA.InventoryUi` (console typing, mouse clicks) fails in a headless NullRHI run (no focused window, no layout) and passes in the rendered run; the headless `SpnGame.Input.ConsoleTyping` test therefore puts the console into its typing state instead of pressing the console key.
* **QA hook left in the game:** with `-SpnQaKeys` only, the UI subsystem writes `pose.txt` ~30 times per second and F5/F9 exist; the flag is never set in normal play.
* `Lvl_SpnMainMenu.umap` is generated by `Tools/create_spn_main_menu_map.py` and is covered by the repository's `*.umap` ignore rule; add it with `git add -f` if it should be tracked.
* The settings screen's graphics rows are disabled when the run cannot change the display (commandlet, no rendering); they were exercised only to the extent shown in the video and the screenshot.

## Not regressions, but easy to misread
* The pause menu always opens on "Resume"; the main menu selects the first enabled entry; keyboard and controller skip disabled entries (the mouse can still hover them).
* A catalog mismatch is never accepted silently; "Load anyway" asks first.
